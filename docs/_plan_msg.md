# 二维码点餐系统项目计划书

## 一、项目概述

### 项目背景
传统餐饮门店普遍采用服务员纸质下单的流程，存在三大痛点：高峰期服务员往返传菜、漏单错单频发；纸质菜单更新成本高；经营数据散落，难以支撑精细化运营。二维码点餐以"一桌一码"为入口，顾客扫码即可浏览菜单、自助下单、在线支付，订单实时推送至后厨，落地价值明确。

### 项目目标
1. 为中小餐饮门店提供开箱即用的二维码点餐系统，覆盖"扫码、点餐、支付、接单、出餐、数据统计"全流程
2. 顾客端零安装、扫码即用，下单耗时明显缩短
3. 商家端可视化管理后台，实时掌握订单与经营数据
4. 系统具备良好扩展性，支持后续外卖聚合、会员营销

### 项目范围
**范围内**：顾客扫码点餐端、商家管理后台、后厨接单端、支付对接（微信支付为主）
**范围外（首期不做）**：堂食外卖复杂配送、会员储值/优惠券营销、多品牌连锁管控

### 成功标准
- 顾客从扫码到完成下单 ≤ 2 分钟
- 订单从确认到后厨收到通知 < 3 秒
- 500 并发下接口成功率 ≥ 99.5%
- 商家可自助管理菜品/桌台/订单

## 二、需求分析

### 用户角色
| 角色 | 说明 | 核心诉求 |
|---|---|---|
| 顾客 | 到店扫码点餐消费者 | 操作简单、下单快、支付安全 |
| 商家（店长） | 门店经营者 | 易上手、实时掌握订单与营业 |
| 后厨 | 接单与出餐人员 | 订单清晰、状态流转顺畅 |
| 系统管理员 | 平台运维配置 | 可维护、可监控、可备份 |

### 功能需求（节选）
扫码入店、菜单浏览、购物车、下单支付、订单状态、后厨接单、菜品管理、桌台码管理、订单管理、数据统计（后两项 P1，其余 P0）

### 非功能需求
性能（P95<500ms）、安全（支付规范/加密/鉴权）、可用性（≥99.5%）、易用性、扩展性

## 三、系统设计
- 总体架构：顾客端（小程序/H5）+ 后厨端 + 商家后台 → 订单/菜单/支付/用户/统计服务 → MySQL + Redis + 对象存储 + 消息队列
- 核心实体：用户、门店、桌台、分类、菜品、订单、订单明细、支付记录（8 张表）
- 订单明细存菜品快照，避免菜品修改影响历史订单

## 四、技术选型
| 层次 | 方案 |
|---|---|
| 顾客端 | 微信小程序 / H5 |
| 商家后台/后厨端 | Vue 3 + Element Plus |
| 后端 | Spring Boot + MyBatis-Plus |
| 数据库 | MySQL 8.0 |
| 缓存 | Redis |
| 消息推送 | RocketMQ / WebSocket |
| 部署 | Linux + Docker + Nginx |

## 五、开发计划与里程碑
需求与设计（8天）→ 开发（12天）→ 测试与上线（8天）
- 需求确认与原型：5天
- 数据库与接口设计：3天
- 顾客点餐端开发：12天
- 后厨与商家端开发：10天
- 支付对接与联调：4天
- 功能测试与修复：5天
- 试运行与部署上线：3天

关键路径：需求设计→开发→支付联调→测试→上线，支付联调为最易阻塞节点

## 六、团队与分工
项目负责人 1、后端开发 1-2、前端开发 1-2、测试 1

## 七、成本预算（估算）
云服务器 1000-3000/年、域名+SSL 100-300/年、对象存储+CDN 200-500/年、微信认证 300/年、开发人力按工时

## 八、风险与对策
支付对接受阻（提前申请资质/备选聚合支付）、高峰并发（Redis缓存/限流）、需求频繁变更（锁定P0范围）、订单状态不一致（状态机+补偿）、数据安全（加密/鉴权/脱敏/备份）

## 九、测试与验收
功能/性能/安全/兼容性测试；验收：P0全通过、支付主流程跑通、性能达标、商家自助管理、试运行一周无重大缺陷

## 十、结论与下一步
需求清晰、方案成熟、成本可控。建议首期锁定 P0 范围分阶段迭代。下一步：确认立项与预算→输出原型与接口文档→启动开发
